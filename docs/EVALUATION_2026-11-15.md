## 1. 공식 4축 채점과 근거

공식 배점은 비공개다(01_contest §1). 아래는 4축 동일 가중(각 25점)으로 본 평가자 추정이다.

### 1-1. 차량특화성 — 17 / 25

| + | − |
|---|---|
| 핵심 입력인 누적 주행거리를 **차가 자동으로** 준다(Odometer). 가족 공동 운전·앱 꺼짐 구간도 다음 실행 때 누적 차이로 회수(실측 통과, PLATFORM_NOTES §9 11-15) | "폰은 모르고 차만 아는 것"이 사실상 **Odometer 하나**다. 심사위원 질문 1순위: "월 1회 계기판 사진 찍어 폰 앱에 넣으면 되지 않나?" 주간 페이스는 하루 이틀 늦어도 비용 결론이 거의 안 바뀐다 |
| "출발 전 정차 화면"이라는 **사용 순간이 차 안에 있다** | 신청서가 내세운 '기어 P→D→P 주행 단위', '요일·시간대 패턴', '내비 등록 목적지'는 **미구현**(예측은 일별 누적 차이의 평일/주말 평균) |
| 주행 중 잠금(기어 + CarUxRestrictions, DO 선언)·이상값 보류·관측/입력/추정 배지 | 앱이 스스로 앞으로 나올 수 없어 "정차 중 한 번 알림"은 **앱을 열었을 때의 배너**다. 차 안 접점은 사용자가 앱을 여는 것에 의존 |

**보완 문장(PT용)**: "폰은 운전자를 알지만 차를 모릅니다. 가족이 탄 거리, 앱이 꺼져 있던 거리까지 차는 압니다. 계약은 사람이 아니라 차의 km로 정산됩니다." 이 프레이밍을 첫 장에 둬야 한다.

### 1-2. 창의성 — 19 / 25

- 02_competitors 기준 근접 클러스터는 운행기록부·차계부(9+편, odolog·autolog·driveledger)와 차량 관리(chageun 등)뿐이고, **계약 약정거리→원 단위 비용→출구 결정**을 다룬 출품작은 확인되지 않았다. 문제 정의(①낮게 잡음 ②못 바꿈 ③단가 착시 ④출구 날짜)가 명확하고 조사(16)가 깊다.
- 감점: 사용 빈도가 본질적으로 낮다(17 결론: "연 몇 번 결정형"). 주간 페이스메이커라는 포장은 이를 덮으려는 설계로 읽힐 수 있다. 보험 특약 모드는 확장성 근거지만 "같은 엔진" 외에 차별 요소는 약하다.

### 1-3. 기술 활용성(Pleos SDK) — 15 / 25

| 실제 사용(코드·실측 근거) | 계획만(신청서에 현재형으로 기술) |
|---|---|
| Vehicle SDK Odometer: check→get→register, 리스너 실측 0.1~1초 반영 | NaviHelper 목적지 조회(코드에 import조차 없음) |
| Vehicle SDK Gear: get/register(SDK에서 deprecated지만 동작) | FusedLocation(없음) |
| AAOS CarUxRestrictionsManager(기어 D·R로 제한 전환 실측) | Pleos TTS(없음) |
| distractionOptimized 선언, 권한 `CAR_DRIVE` 1개 | Room/DataStore(실제는 kotlinx.serialization JSON 파일) |
| OdometerIngestor: 역행·급증(250km/h) 보류, 세션 공백 회수, 재구독 중복 방지 — 단위 테스트 12개 | 예측 오차(월말 실측 대비) 누적·신뢰도 표시(코드에 없음) |

- 공개 SDK 5종 중 **Vehicle 1종만** 사용. 상위작(마중·Motion Zero·Statio)은 3~5종을 핵심 경험에 엮었다(02 §5). 다만 '제어(set) 비의존', 'capability·실패 시 0 대체 금지', '백그라운드 콜백 정지 실측 후 세션 설계' 같은 **엔지니어링 성숙도는 상위권**이다.
- 위험: 심사위원이 신청서 "활용 차량 데이터와 SDK/API" 6항목을 GitHub 코드와 대조하면 3항목이 비어 있다. "계획을 구현처럼 쓰지 말라"(01 §2 공식 안내)에 걸린다.

### 1-4. 사업성 — 13 / 25

- 산정이 정직하고 검산된다: 2027 Pleos 탑재 약 20만 대(추정) × 개인 렌트·리스 11% ≈ 2.2만 대 × 설치 10% = 2,200명, 보험 특약 6,000명 → MAU (2,200+6,000)×0.6 ≈ 4,900. 표기 규칙([추정]/[가정])도 지킨다.
- 그러나 숫자 자체가 작다. 17번 문서 스스로 "렌트·리스 1차 타깃만으로는 '굳이?'가 맞다"고 결론 냈다. 주간 재방문 50%·12개월 30% 가정은 '연 몇 번 결정형' 성격과 충돌한다.
- 사업 모델(결정 패키지 이용권, 렌트·리스사 제휴, 보험사 연계)은 그럴듯하지만, **현대캐피탈(그룹 캡티브)과의 인도 시점 제휴**라는 가장 강한 카드가 한 줄로만 묻혀 있다. 주최 측이 보기에 그룹 내 시너지(현대캐피탈·현대해상 아님·현대차 인증중고)가 가장 설득력 있는 지점이다.

### 3-4. 심사관이 APK로 돌릴 때의 위험

1. **어떤 APK를 내는가**: release 빌드는 `DEMO_PANEL=false`라 시연 진입 버튼이 없고 서명 설정도 없다. demo APK는 Android Debug 인증서. 제출 규격은 `apk/팀명_앱이름_release.apk`. → demo 빌드를 release 파일명으로 내면 '이름과 실체 불일치', release를 내면 심사관은 0km 빈 상태만 본다. **demo 기능을 켠 release 서명 빌드**가 정답.
2. **첫 실행 3초 판독 4/10**(ux/reviews 1510): 시연 진입 버튼이 앱 밖 12sp 띠, 앱 정체 문장 없음. 심사관이 직접 계약을 입력하면 0km 첫날이라 가치를 못 본다.
3. **사용자 10**: `pm clear` 등에 `--user 10` 필요 — README에 없으면 재설치해도 데이터가 남아 혼란.
4. **VC 0km 리셋**: 에뮬레이터 재부팅 시 VC 주행거리 0 → 이전 데이터가 역행 보류. 재기준 경로는 있으나 심사관이 이해하기 어렵다.
5. `android.hardware.type.automotive required=true` → 일반 폰·태블릿에 설치 불가(의도된 것이지만 README에 명시 필요).
